How we work on Contexia

You steer product and technical decisions. The agent researches, builds, verifies and keeps the project's memory. This page shows where your attention is needed and what runs without it.

The flow, and where it needs you

Seven phases, matching how you already work. There are no commands to learn: you say what you want in your own words and the agent picks the procedure. A shaded cell under "You" means the phase waits for you. Everywhere else you get a short summary you are free to ignore.

It is a loop: a validation finding or a surprising experiment sends work back to an earlier phase. Ask “where are we?” at any moment to get the current status.

Who decides what

You decide
  • Product behaviour: what a person sees and can do
  • System shape: the main parts, their boundaries, the stack
  • Contracts: what each service promises the others
  • Qualities: how reliable, how fast, what is guaranteed
  • Anything expensive to reverse
Agent decides
  • Code structure, naming, file layout
  • Libraries and patterns inside a component
  • How tests are written
  • The order of small steps inside a task

Notable choices are listed for you in one line each. You can overrule any of them.

What you say is treated as direction. When a direction and the goal pull apart, the agent says so and proposes an alternative before acting.

Example · how commits happen · decided: A

Why now. Once work starts, something will be finished and verified many times a day.

A. The agent commits at verified checkpoints

Chosen
Upside
Every verified step is a restore point. You are not interrupted about code you do not review.
Risk
A commit lands without your eyes on it. Limited by the check that must pass first, and nothing is pushed without asking.
Undo
Cheap. Change the rule at any time.

B. The agent asks before every commit

Upside
You see every checkpoint as it happens.
Risk
Many small interruptions, and work stalls whenever you are away.
Undo
Cheap.

Best practice. Agent-driven projects commit small and often, so any step can be rolled back, and people review outcomes instead of individual commits.

Recommendation. A, directly on main, with every push still asking first.

Where the project's memory lives

Nothing important lives only in a chat. A new session starts from these files, so you never have to repeat yourself.

Loaded into every session
  • CLAUDE.mdThe working agreement and the rules on this page
  • tasks/board.mdWork in flight, and what is waiting on you
  • docs/decisions/README.mdEvery decision in one line
  • docs/guardrails.mdWhat must stay true, and the check that holds it

Kept short on purpose. A crowded context makes an agent worse, not better.

Opened when needed
  • docs/brief.mdThe goal, word for word
  • docs/research/ · experiments/The evidence behind decisions
  • docs/decisions/D-nnnThe full reasoning for each decision
  • docs/contracts/What services promise each other
  • docs/visuals/Pages like this one
  • tasks/T-nnn · tasks/done.mdAcceptance criteria, evidence, history

Everything traces: a task points to its decision, a decision to its evidence, a guardrail to its decision and its check.

Defaults chosen for you, all changeable
  • The agent does not ask before routine steps: reading, running checks and tests, editing files inside the current task, updating the board.
  • One board file instead of a tracker tool: fewer moving parts for a prototype.
  • Decisions are permanent records. A change of mind adds a new record that replaces the old one, so the history of why stays readable.
  • Visuals are plain HTML files in the repository. Nothing is published anywhere.
  • IDs keep things traceable: T tasks, D decisions, G guardrails, R research notes, E experiments.
  • Commit messages carry the task ID, so the history can be searched by task.
