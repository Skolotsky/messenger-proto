Growing by adding: copies, databases, nothing else

The question is not whether the design survives some number of organizations, but whether anything in it cannot be grown by adding more of the same: for the number of organizations, and for the size of one. One rule answers it for every part. An independent check broke my first version of this page in four places; the answers are below, by analysis and small simulations.

The rule

Every piece of state belongs to one organization, and every program either keeps its state in PostgreSQL or keeps only memory about the organizations routed to it. Nothing is shared between organizations except a small directory that says which database holds which organization. So more organizations never make any single thing bigger; they are spread.

Three things in the design that would not have grown, now removed

removed Waking workers through the database on every save

Convenient at small size, and a hidden queue everybody shares. Measured: saving dropped from 9,549 to 2,043 changes a second. Workers now ask one cheap question every few tens of milliseconds.

removed "I am still looking at this" written to the log every 20 seconds

Three log entries a minute for every person with a conversation open: more than all messages, reactions and reads together, and each one passed on to the feed. Now only the start and the end are written.

removed Asking every organization in turn whether it has work

The cost grows with the number of organizations even when nothing happens. Measured with 5,000: 719 ms a round. The question that replaced it first read every organization's row and was itself replaced by an index of the organizations that have work.

How large can one organization be? (D-030, by analysis)

Assumptions: a person causes about 150 changes a working day, so about 0.02 a second at the busiest time; a typical production PostgreSQL confirms a small save in 1 to 3 ms. In an organization three things happen one at a time, and each sets a ceiling.

Today

About 5,000 people in one organization comfortably. Up to 10,000 to 25,000 with delays after large announcements.

For larger organizations

A path, with no number (D-034). Conversations applied in parallel, grouped saves, big-channel items stored once, and batched calls to search. None is built in the first version, where the seeded team has 36. This is also where one copy of Conversations holding all of one organization's connections ends.

Beyond that

A numbered log per conversation instead of per organization. Possible, and a real redesign: every contract's numbers and the screen's catch-up change. Not adopted.

Held from the first version, so that all of this stays possible (G-030): the feed's result for a conversation depends only on that conversation's changes, in their order, and on reader-wide changes at their place. Checked in a small simulation on a subset of the rules (E-008): 200 different interleavings of conversations gave the same feed every time; with the reader-wide changes moved, never. The real proof is this guardrail's test on the product's own rules.

These figures are estimates from the assumptions stated, not measurements.

So: a cache, with many organizations?

Still none, and now for a stated reason. A shared in-memory store such as Redis is needed when copies of a program must share something: who is connected where, how many messages an agent sent this minute, a wake-up for everyone. Here each organization is served by one copy, so that copy's own memory is enough, and workers are not woken at all. Inside the feed program, keeping readers' settings in memory while it works is an ordinary optimisation and not a second source of truth. If screens of one organization ever had to be served by several copies, that would be the moment for a shared store.
