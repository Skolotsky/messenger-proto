The build: nineteen packages in five waves

Two packages come first and are done in sequence. After them, up to six run side by side, because each one is built against the written contracts and a stand-in for its neighbours, not against the neighbours themselves.

Needs you

Is this the plan to hand to a new session? One thing in it is yours to settle first: the guardrail tests are protected, so writing them for the first time will ask for your approval each time. I suggest protecting each test from the moment it has passed once, not before.

A package needs only what is to its left in its own row, plus wave 0. The joining packages need what their row and the rows above them built.

Why they can run side by side

They meet only through the contracts

Wave 0 turns the seven contracts into schemas with examples. A package is right when it keeps its side of them. Two packages never need each other's code.

Each has a stand-in for its neighbours

A log writer plays Conversations for the workers, the feed and the stand-ins. A recording receiver plays the receivers for the workers. A mock door plays the whole server for the web app.

Each owns its folders

A package changes only its own directories, in its own working copy. Shared files change only between waves, by the session that leads. Joining happens in wave 3, where a mismatch shows up as a failing test.

How it is verified

A package is done when its acceptance points are checked, its guardrail tests were seen to fail and then pass, the full verification passes, and the real thing was run and looked at.

Tests use seeded randomness and a clock they control, so five seconds, a minute or seven days pass instantly. Timed tests run for about a minute at the seeded team's size, never at large sizes.

The three milestones

1 · The spine runs end to end (T-057)

A message, an edit and a delete travel to search, the feed and the notification sender. Every delivery guardrail passes with programs being killed, with two copies of the workers and the feed, and with two organizations on two databases.

2 · A person can use it (T-058)

The web app on the real programs, at both widths. A screen that lost its connection ends right; a part that is behind says so.

3 · Validation (T-061)

A fresh agent checks the running product, with the busy seeded team, against the brief, every contract and every guardrail.

What the plan does not build

Sign-in and permissions; creating organizations; real push; a second copy of Conversations in production form, trimming of old data and an entry point that routes by organization (the tests use a small router to prove the design allows them); the three measures for very large organizations (D-030). The text rules judged by a model come last, after their own experiment.
