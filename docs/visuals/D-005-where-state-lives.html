Where state lives

Everything that must survive a restart is in PostgreSQL, in one area per part. Memory holds only things that can be lost and rebuilt. There is no Redis and no cache layer.

The picture

In PostgreSQL, part by part

Each part has its own area and its own database login, and cannot read another's (G-008). Every table carries the organization, and the database refuses a row of another organization (G-025). Table names are working names; the exact columns are settled in the first build task.

Why no Redis or other cache

Nothing needs it at this size

One PostgreSQL saved about 9,500 changes a second in the test (E-007). The seeded team produces a few hundredths of a change a second. Workers ask one cheap question, "which organizations have work?", every few tens of milliseconds.

A cache is a second copy to keep true

Most of the guardrails say "equals the truth". Every cache would be one more place that can be stale after an edit or a delete, with its own tests. The feed already is the one deliberate copy, and it is rebuilt from the log.

And with many organizations?

Still none (D-029). A shared store such as Redis is needed when copies of a program must share something. Here everything of one organization is served by one copy, so that copy's own memory is enough. If screens of one organization ever had to be served by several copies, that would be the moment.
